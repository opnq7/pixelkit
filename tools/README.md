# 多智能体分工机制

主智能体（Claude Opus 5.5）当主管：拆任务、写任务单、验收、整合、做所有需要品味和全局判断的事。
本机其他 AI 当执行者。目标：**省主智能体的 token，同时不降低交付质量；主智能体掉线也不丢进度。**

> 不为多智能体而多智能体：一个任务交代清楚所需的文字，比主智能体自己做完还长，就自己做。

---

## 1. 执行者

| 代号 | 是什么 | 能力 | 默认模型 | 用来做 |
|---|---|---|---|---|
| `ds` | DeepSeek 纯文本 API | 只回答，不碰文件；最便宜、最快（几秒） | `deepseek-flash`（V4.1 Flash），**effort 默认 high**（用户定的；纯格式活可 `--effort low`） | 文案改写 / 变体、摘要、翻译、提取成 JSON、生图提示词变体、列多音字、检查字数 |
| `ds-agent` | Claude Code CLI 接 DeepSeek 后端 | 能读写文件、跑脚本 | `deepseek-flash`；难一点用 `deepseek-v4-pro` | 批量文件处理、写有明确验收的小脚本、按现有模板加组件、跑分析脚本并汇总 |
| `codex` | Codex CLI（GPT） | 能读写文件、跑脚本、**生图** | `gpt-6.1-sol` effort high | 日常生图（背景板、道具、角色草图）、中等代码任务 |
| `codex` + `--model gpt-6-astra` | 同上，强模型 | 同上 | `gpt-6-astra` | 难的生图（多元素构图、风格锁定、反复改不对的）、难的独立代码任务 |
| Sonnet 5.5 | 主智能体自己的 Agent 子智能体 | 和主智能体同一套工具（看图、读视频帧、浏览器） | `sonnet` | 前两家做不好时补位；需要看图判断的检查；代码审查；**同时最多 2 个** |

**优先级**：`ds` → `ds-agent` → `codex` → Sonnet。同一档能做的，选更便宜的。

实测（2026-11-08）：
- `ds-agent` 读导演稿写 CSV：18 秒一次做对，汇报格式规范。
- `ds` 判断类小题（多音字）：关掉思考（`--effort none`）会答错「行长」；`low` 能答对。题目问得含糊时它会想很久（6000 思考 token、43 秒）还列出一堆不相干的字。
  → 给 `ds` 的题要具体、给判断标准；能用脚本确定的（多音字 → pypinyin、字数 → 正则）就别问模型。
DeepSeek 余额：`python 协作/dispatch.py balance`（2026-11-08 为 11.92 元）。

## 2. 难度分级：什么能派、派给谁

| 级别 | 特征 | 派给 |
|---|---|---|
| **L1 机械** | 输入输出都明确，对错一眼看得出；不需要项目背景 | `ds`（纯文本）/ `ds-agent`（要碰文件） |
| **L2 有边界的执行** | 要写代码或生图，但有**可以自动检查的验收标准**（脚本跑通、图片尺寸 / 风格符合、测试通过）；需要的背景 ≤ 30 行就能交代清楚 | `ds-agent`（flash → pro）或 `codex`（sol）；生图一律 `codex` |
| **L3 需要品味或全局判断** | 分镜、导演稿、配音情绪、美术方向、节奏、选题、文案主体、架构决定、最终质检、任何用户会评价「好不好看 / 好不好听」的东西 | **主智能体自己做**。执行者只能给它跑腿（出候选、跑数据） |

**永远不派出去的**：
- 交付前的最终验收和整合（执行者的「完成」不算数，主智能体抽查过才算）。
- 需要这段对话里大量上下文才做得对的事（交代成本高于自己做）。
- 删文件、改密钥 / 配置、联网下载可执行文件、发消息、发布。
- 用户明确表达过口味的环节（配音、美术）的取舍。

**升级规则**：同一个任务失败 2 次（含返工）就升一级执行者（ds → ds-agent → codex sol → codex astra → Sonnet → 主智能体自己），**不在同一个执行者上试第 3 次**。

## 2.5 生图的分工（2026-11-08 实测）

Codex 的生图工具只有一个（`image_gen.imagegen`，参数只有提示词和参考图），**画图的底层模型不能选**。
sol / astra 的区别只在「谁写提示词、谁判断好坏」。同一个任务（吉祥物全身图 + 9 件拆件图）三组对比：

| 组 | 提示词 | 用时 | Codex token | 生成次数 | 拆件能不能直接绑骨 |
|---|---|---|---|---|---|
| **主智能体写 + sol low 照用** | 主智能体 | **229 s** | **7.6 万** | 2 | **最好**：手臂直、两端圆头，手带拇指 |
| astra 自己写 | astra | 330 s | 8.6 万 | 2 | 能用，但手臂弯、头身比例偏 |
| sol 自己写 | sol | 611 s | 10.2 万 | 5 | 件太小、手臂弯，自己反复重画也没修好 |

→ **规则：生图提示词一律由主智能体写**（构图、配色、拆件方式是美术判断，也依赖后面的动画做法），存成 `.txt` 和图放在一起；
Codex 用 `gpt-6.1-sol --effort low` 逐字执行、只生成一次；主智能体看图决定要不要改提示词重来。astra 留给需要它自己看图迭代的难活。

**出图提速（实测，3 张道具图）**：

| 做法 | 3 张总耗时 | 说明 |
|---|---|---|
| 旧：任务单让 Codex 读提示词文件、读生图技能文档、复制、自检 | 约 138 s / 张 | 时间大多花在读文档和跑命令上 |
| 一个会话里要求「并行」调 3 次 image_gen | 112 s | **同一会话内生图是串行的**（41 / 73 / 100 s 各出一张） |
| 3 个 Codex 进程同时跑，各出 1 张 | 63 s | 真并行；图在 37–46 s 落盘，进程再空转 10–17 s 才退出 |
| **`dispatch.py img`**：3 进程并行 + 精简指令 + 看到图就结束进程 | **43 s** | 现在的默认做法，约为原来的 1/10 |

```bash
python 协作/dispatch.py img plates/宫殿.txt plates/街景.txt plates/书房.txt          # 每个 .txt 一条提示词 → 同名 .png
python 协作/dispatch.py img props/*.txt --par 4 --ref 风格参考.png                     # 最多 4 路；带参考图
```
- 提示词（主智能体写）存成 `.txt`，图出在旁边的同名 `.png`，正好符合「提示词和图放在一起」的规矩。
- **道具 / 单个物件加 `--alpha`**：直接出真透明背景（实测 50 s，边缘干净），不用再抠品红。场景背景板不加。
- 调度器自动用本机最新的 Codex（桌面版自带的 codex.exe 0.167 比 npm 装的 0.148 新）。
- **Images 2.6 的动图 GIF**（2026-11-04 发布）：命令行里的画图工具没有动画参数，实测要求出 GIF 只得到静态 PNG。
  只能在 ChatGPT / Codex 的界面里手动出，或者走 OpenAI API（要单独的 API key 和费用）。对我们用处也不大：
  AI 动图每帧像素网格不一致、帧率低、对不上配音时间轴；我们的动画一律由代码驱动。
- 每张图一个进程、只读沙箱、不跑命令，失败或超时（默认 240 s）自动重试 1 次；额度用完标 `quota`。
- 并发受总槽位限制（≤ 4）：渲染在跑时就少开几路。

**踩坑**：
- 并行任务**必须各用独立的输出目录**；派发前检查任务单里的路径（这次 heredoc 里的 `$M` 没展开，两个任务写进了同一个目录，文件互相覆盖，只能靠 `~/.codex/generated_images/<会话>/` 按时间找回）。
- Codex 沙箱里经常调不到 python（会改用 PowerShell 验收），任务单里的自检别依赖 python。
- 背景色 GPT 不一定守规矩（有时给透明底、有时给近似品红），`puppet.key_out` 两种都能处理。

## 3. 并发与电脑负载

- **同时最多 4 个**（所有执行者 + Sonnet + 重 CPU 任务合计）。`dispatch.py run` 满载时直接拒绝（exit 3）。
- Sonnet 子智能体和本地重任务（pixelkit 渲染、whisper、demucs）不经过调度器，**开始前登记、结束后释放**：
  `dispatch.py hold sonnet1 "审查 xx"` / `dispatch.py free sonnet1`；`hold render "s03 全片"`。
- 渲染（8 进程）在跑时，最多再并行 2 个**联网型**执行者（ds / codex 主要耗网络，不耗本机 CPU）。
- Codex 是 ChatGPT 订阅额度，会用完（调度器识别后标 `quota` 并给出恢复时间）。额度用完时：代码任务降到 `ds-agent`（pro），生图任务排队等恢复，不用别的模型凑。

## 4. 节省主智能体 token 的规矩

1. **任务单一次写清楚**（模板：[任务单模板.md](任务单模板.md)）：目标、输入路径、产出路径与格式、验收标准、禁止事项。宁可多写 3 行，不要来回返工。
2. **交付物落盘，主智能体只读汇报**：执行者最后一条消息 ≤ 12 行（状态 / 产出 / 验证 / 问题），调度器已经在前缀里强制。
3. **验收靠抽查和机器检查**，不通读：跑一下脚本、看一张联系表、`python -m pixelkit.qa`、对比字数，而不是把执行者写的东西全部读进上下文。
4. 大段素材（转写稿、日志、长文）先交给 `ds` 压缩成要点再给主智能体看。
5. 互不依赖的任务一次性并行派出，不串行等。

## 5. 进度检查：多久看一次

- 执行者用 `Bash(run_in_background)` 跑 `dispatch.py run ...`：**任务结束时 harness 自动通知主智能体，不轮询**。
- 每个任务有硬超时，到点调度器结束整个进程树并标 `timeout`，所以「卡死」也一定会通知回来：
  `ds` 5 分钟、`ds-agent` 15 分钟、`codex` 25 分钟（生图建议 `--timeout 600`）。可用 `--timeout` 改。
- 主智能体在等待期间做自己的 L3 工作；**有多个任务在跑、且超过 10 分钟没有任何通知时**，跑一次 `dispatch.py status` 看是否有 `⚠超时` 或 `orphan`。
- 长流程（一整期视频）每完成一个阶段，更新一次 [交接.md](交接.md)。

## 6. 主智能体掉线 / 上下文被压缩后的恢复

所有状态都在磁盘上，不只在主智能体的脑子里：

| 文件 | 内容 | 谁写、什么时候写 |
|---|---|---|
| `协作/交接.md` | 当前目标、已完成、在跑的任务 ID、下一步、已做的决定和用户的偏好 | 主智能体：每个阶段结束、每次并行派发前、预感对话很长时 |
| `协作/任务/<ID>/prompt.md` | 发出去的完整任务单 | 调度器自动 |
| `协作/任务/<ID>/out.md` | 执行者的汇报 | 调度器自动 |
| `协作/任务/<ID>/meta.json` | 状态、模型、耗时、token、退出原因 | 调度器自动 |

**恢复步骤**（新会话 / 压缩后第一件事）：
1. 读 `协作/交接.md`。
2. `python 协作/dispatch.py status`：
   - `done` 还没验收的 → `show <ID>` 读汇报、抽查产出；
   - `orphan`（进程没了但没写完）→ 看产出路径里有没有半成品，删掉半成品后用同一个 `prompt.md` 重跑；
   - `quota` / `timeout` / `failed` → 按第 2 节升级规则换执行者。
3. 把恢复后的状态写回 `交接.md`，继续。

## 7. 命令速查

```bash
python 协作/dispatch.py run ds 任务单.md                     # 文本小活
python 协作/dispatch.py run ds-agent 任务单.md --model deepseek-v4-pro
python 协作/dispatch.py run codex 任务单.md --timeout 600    # 生图 / 代码（gpt-6.1-sol high）
python 协作/dispatch.py run codex 任务单.md --model gpt-6-astra
python 协作/dispatch.py run codex 任务单.md --image 参考图.png   # 带参考图
python 协作/dispatch.py status
python 协作/dispatch.py show <ID>
python 协作/dispatch.py hold sonnet1 "说明"   /   free sonnet1
python 协作/dispatch.py balance
```

## 8. 密钥

DeepSeek key 在 `协作/secrets.local.json`（环境变量 `DEEPSEEK_API_KEY` 优先）。这个文件不要分享、不要放进素材包；
key 出现过在聊天记录里，项目告一段落后去 DeepSeek 控制台换一个新的，只改这个文件即可。
Codex 用本机 ChatGPT 登录（`~/.codex/auth.json`），不需要 key。
